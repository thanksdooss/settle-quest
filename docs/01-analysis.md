# 1단계 · 원자료 분석과 제품 설계 결론

> 작성 2026-09-21. 원자료는 비공개 로컬 경로에서만 읽었고, 이 문서에는 인용 요약만 남긴다.
> 학교·지역·팀원 실명은 일반화했다.

## 1. 확인한 원자료

| 자료 | 형식 | 이 프로젝트에 주는 것 |

| 창업 경진대회 참가신청서 | hwpx (본문 확보) | 문제 정의, 인터뷰 수치, 수익 모델, 로드맵 |

### 근거로 쓸 수 있는 수치 (문서에서 직접 확인됨)

- 같은 관공서 2회 이상 재방문 **86.7%**
- 공식 채널보다 비공식 경로(선배·지인) 의존 **76.7%**
- 유료 지불 의사 **80%**, 대표 구간 **건당 1~3만 원**
- 인터뷰 대상 명부 33행(유학생 30 + 지자체 1 + 소상공인 1 + 예정 1), 국적 10개국 이상
  (네팔·베트남·일본·우간다·이집트·카타르·터키·우즈베키스탄·말레이시아·태국·멕시코)
- 전국 평균 중도 탈락률 7.1% — 보고서가 인용한 외부 수치. **우리가 검증한 값이 아니므로 제품·케이스에 쓰지 않는다.**

### 확인하지 못한 수치

- "유학 시작 비용 1,100만 원 중 200만 원이 브로커 수수료" — 지시문에는 있으나 **텍스트 추출이 가능한 문서에서는 찾지 못했다.** 이미지로만 남은 발표자료에 있을 가능성이 높다.
  → 케이스에 쓸 때는 "팀 인터뷰에서 보고된 개별 사례"로만 표기하고, 대표 수치로 승격하지 않는다.

## 2. 인터뷰가 실제로 말한 것 (제품 원칙의 출처)

문서에 남은 익명 인용 중 제품 설계를 직접 결정한 것:

1. **"학교에서 준 안내문이 작년 정보인 것 같아 불안했다."**
   → 문제는 정보의 부재가 아니라 **신선도에 대한 불신**이다. 그래서 이 제품의 1급 기능은 "마지막 확인일"이다.
2. **"'기본증명서'라고만 쓰여 있으면 내 나라에서는 뭐가 그건지, 아포스티유가 필요한지 알 수 없다."**
   → 절차 규칙은 **국적·비자 조건을 가진 데이터**여야 한다. 하나의 문장으로는 답이 안 된다.
3. **"검증된 서비스에 2~3만 원 내는 게, 선배에게 비싼 밥 사며 묻는 것보다 낫다."**
   → 파는 것은 편리함이 아니라 **확실성**. 따라서 확실하지 않을 때는 확실하지 않다고 말해야 가치가 유지된다.
4. **"A지점과 B지점이 요구하는 서류가 달랐다."**
   → 같은 절차도 기관·지점에 따라 갈린다. 규칙에 **적용 조건(기관)** 필드가 필요하다.

심사위원 피드백에서 가져온 것: "파파고와 뭐가 다른가"에 대한 답은 번역 품질이 아니라 **행정 문서에 한정된 용어 병기와 서식 자동 채움**이다. 일상 번역은 하지 않는다.

## 4. 이 제품의 진짜 문제 — 정보 신선도

절차는 국적·비자·기관에 따라 갈리고 학기 중에도 바뀐다. 하드코딩하면 사용자가 불평한 바로 그 문제를 재현한다.
그래서 구조를 이렇게 잡는다.

### 4.1 절차 규칙 = 버전 있는 데이터 (YAML)

```yaml
id: alien-registration
title:   { ko: 외국인등록, en: Alien Registration, vi: Đăng ký người nước ngoài }
terms:   [{ ko: 외국인등록증, en: Alien Registration Card (ARC) }]
applies_to:
  visa:   [D-2, D-4]          # 없으면 전체
  nationality: { except: [] } # 특정 국적만/제외
  issuer: [출입국·외국인청]
requires: [passport, admission-certificate]   # 선행 조건 = 그래프 간선
deadline: { from: entry_date, days: 90 }
steps:    [...]
documents:[...]
sources:
  - url: https://www.hikorea.go.kr/...
    checked_by: maintainer
    checked_on: 2026-09-21
    next_check_on: 2026-12-20
    content_hash: sha256:...
status: verified            # verified | needs_review | stale  ← 코드가 계산, 손으로 쓰지 않음
```

핵심은 `status`를 **사람이 적지 않고 날짜로 계산**한다는 것이다. 방치하면 자동으로 나빠진다.

### 4.2 신선도 상태 기계

```
verified   확인일 ≤ 90일                    → 화면에 "2026-09-21 확인"
aging      90일 초과, next_check_on 이전     → 같은 표시 + 점검 예정일 노출
stale      next_check_on 경과               → "확인 필요" 배지, 절차 본문 위에 경고
changed    원문 해시가 달라짐                → "확인 필요" + 검토 큐에 자동 등록
```

`stale`/`changed`인 절차는 **개인화 목록에서 숨기지 않고, 경고를 달아 그대로 보여 준다.** 틀린 답보다 "모른다"가 낫다는 원칙의 구현이다.

### 4.3 변경 감지와 검토 큐

GitHub Actions 주간 크론이 각 `sources[].url`을 받아 본문 텍스트를 정규화·해시하고, 이전 해시와 다르면
`content_hash`를 갱신하는 대신 **이슈를 열고 규칙을 `needs_review`로 표시**한다. 사람이 확인해야만 `checked_on`이 올라간다.
→ 규칙 이력은 **Git이 곧 버전 테이블**이다. 누가·언제·무엇을 바꿨는지 `git log`로 증명된다.

### 4.4 커버리지 지표

`90일 이내 확인된 규칙 / 전체 규칙` 을 빌드 시 계산해 대시보드와 README 배지로 노출한다.
이 숫자가 낮아지면 제품이 스스로 그 사실을 드러낸다.

## 5. 구현할 절차 (초판 7개)

선행 관계 그래프. 화살표는 "먼저 필요함".

```
여권·비자 (전제)
   ├─→ 외국인등록 ──→ 체류지 신고(주소 변경)
   │        ├─→ 은행 계좌 개설
   │        ├─→ 휴대폰 개통          (일부 통신사는 ARC 전 개통 가능 — 조건 분기)
   │        └─→ 시간제 취업허가
   └─→ 국민건강보험 가입 (가입 시점은 비자·체류기간에 따라 분기)
```

1. 외국인등록 2. 체류지(주소) 변경 신고 3. 휴대폰 개통 4. 은행 계좌 개설
5. 국민건강보험 가입 6. 시간제 취업허가 7. 외국인등록증 수령·분실 신고

각 절차는 출처 URL(하이코리아, 법무부, 건보공단 등)과 확인일을 달고 들어간다.
**내가 실제로 원문을 확인한 절차만 `verified`로 두고, 나머지는 `needs_review`로 커밋한다.** 빈칸을 그럴듯하게 채우지 않는다.

## 6. 스택 — 서버를 두지 않는 쪽을 권한다

지시문은 FastAPI/Spring + PostgreSQL을 열어 두었지만, 분석 결과 **정적 PWA + Git을 규칙 저장소로 쓰는 구성**을 기본안으로 제안한다.

- 규칙 버전 이력의 요구사항(누가·언제·무엇을)은 **Git이 이미 완전히 만족**한다. DB에 같은 걸 또 만들면 이력이 둘로 갈린다.
- 여권 이미지는 기기 안에서 처리하는 것이 절대 규칙이다. **서버가 없으면 유출 경로 자체가 없다** — 면접에서 가장 강한 답이 된다.
- 개인 프로필·채운 서식은 브라우저(IndexedDB)에만 두고, 내보내기/삭제 버튼을 붙인다.
- 배치(변경 감지)는 GitHub Actions 크론. 서버 상주 프로세스가 필요 없다.

| | 기본안 (정적 PWA + Git) | 대안 (FastAPI + PostgreSQL 추가) |
|---|---|---|
| 규칙 이력 | git log / PR | 테이블 + 마이그레이션 |
| 개인정보 | 서버에 아예 없음 | 저장 안 해도 "안 보낸다"를 증명해야 함 |
| 운영 비용 | 0 | 상시 비용 |
| 포트폴리오 | 설계 판단을 설명하는 재료 | 백엔드 이력 한 줄 |

→ **기본안으로 진행하되, 백엔드 경험을 남기고 싶다면 "검토 큐 API + 규칙 이력 조회"만 담은 얇은 FastAPI를 2단계 후반에 얹는다.** 이 결정은 확인이 필요하다.

확정 스택: Vue 3 + TypeScript + Vite + PWA / Pinia / vue-i18n / Tesseract.js(MRZ) / Vitest + Playwright / GitHub Actions.

## 7. 문서 도우미 범위

- 여권 **MRZ(TD3, 44자 2줄)** 만 읽는다. 얼굴면 전체 OCR은 하지 않는다 — MRZ는 **체크디지트가 있어 스스로 검증**되기 때문이다. 판독 실패를 "그럴듯한 오답"이 아니라 "실패"로 확정할 수 있다.
- 추출 항목: 영문 성/이름, 생년월일, 성별, 국적, 여권번호, 만료일. 모두 편집 가능.
- 채우는 서식: 통합신청서 계열의 공통 칸. 서식 PDF를 재배포하지 않고 **입력값만** 보관·출력한다.
- 이미지는 메모리에서만 다루고 저장하지 않는다. 저장되는 것은 사용자가 확인한 텍스트 값뿐이다.

## 8. 다국어

한국어 · 영어 · **베트남어**. 세 번째 언어를 베트남어로 정한 근거는 인터뷰 명부에서 베트남 국적이 가장 많았다는 사실이다.
행정 용어는 **원문 병기 고정**(예: 외국인등록증 / Alien Registration Card / Thẻ đăng ký người nước ngoài). 번역만 남기지 않는다.

## 9. 법적 고지

- 모든 절차 화면 하단과 첫 진입 화면, README에 "행정 정보 안내이며 법적 효력이 없습니다 / 개별 사안은 관할 기관에 확인하십시오"를 고정 노출.
- 개인 상황에 대한 단정(예: "당신은 비자 연장이 가능합니다")을 출력하지 않는다. 규칙은 **조건과 출처**를 보여 줄 뿐 판단하지 않는다.

## 10. 남은 위험

| 위험 | 대응 |
|---|---|
| 공공기관 페이지가 JS 렌더링이라 해시 비교가 불안정 | 정규화 규칙(공백·날짜·세션토큰 제거) 후 해시. 실패 시 규칙을 `needs_review`로 떨어뜨린다 |

| 규칙이 실제로 오래되어 사용자가 손해 | 법적 고지 + `stale` 경고 + 관할 기관 연락처 병기 |
